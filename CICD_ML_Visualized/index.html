CI/CD for machine learning

Every time something changes (the code, the data or the model), a robot runs the same checklist: check → train → test → package → release carefully → watch. If any step fails, it stops before users are affected. That robot is the CI/CD pipeline.

👋 New here? The 30-second version

🧸 Think of it like this

A restaurant kitchen. Every new dish is tasted by the chef before it goes to the guests (CI). Then it's first served to one table. If they like it, it goes on the menu for everyone (CD). A waiter keeps asking guests how it tastes (monitoring).

📖 Hard words, made easy:
CI (Continuous Integration) = check every change automatically CD (Continuous Delivery / Deployment) = release every good change automatically and safely CT (Continuous Training) = retrain automatically when new data arrives Pipeline = the fixed list of steps the robot runs Quality gate = a rule a model must pass to go further Model registry = a shelf of numbered models, one labelled "production" Canary = give the new model to a few users first

① Why do we need it?

😰 Without a pipeline (by hand)

  1. "It works on my laptop." The model was trained with a different library version, and in production it gives other answers.
  2. Nobody ran the tests. A tiny change in preprocessing flips the image colours. Accuracy silently drops.
  3. Which model is live? "model_final_v2_NEW.pth"… trained on which data? Nobody knows.
  4. Rollback takes hours. Someone must find the old file and copy it to the server at night.

😌 With a pipeline (automatic)

  1. Same steps every time, in a clean, identical environment (a container).
  2. Tests and data checks run on every change, in minutes, not "when someone remembers".
  3. Every model has a version and a recipe: this code + this data + these settings.
  4. Rollback is one click: point "production" back to the previous version.

② What is different in ML?

In normal software only the code changes, so CI/CD tests the code. In ML, the result also depends on the data, and the model is created by training. Each one can break things, often silently (no error message, just worse answers).

💻

Code

Preprocessing, model architecture, the API.

Silent failure: images resized to 64 instead of 96. It still runs, but accuracy drops.

Checked by: unit tests, lint.

📊

Data

New pictures, new labels, a new source.

Silent failure: a camera update makes all photos darker; 10% of labels are missing.

Checked by: schema checks, statistics, drift checks.

🧠

Model

The result of training on code + data.

Silent failure: overall accuracy is fine, but the "cat" class got much worse.

Checked by: evaluation against a quality gate and against the current model.

The whole story
    Detailed: what each step really checks
    StepTypical checks
    🧹 Code checksLint/format, unit tests (preprocessing shape and range, label mapping), a tiny "smoke" training on 50 pictures to prove the code runs.
    📊 Data checksSchema (columns, types, image size), missing values, class balance, duplicates, and train–test leakage. Drift: compare statistics with the last training set.
    🏋️ TrainFixed seed, pinned library versions, data version recorded, all parameters logged (experiment tracking).
    🎯 EvaluateMetrics on a fixed test set, compared with thresholds and with the current production model. Per-class recall, latency, size, fairness slices.
    📦 PackageExport (e.g. ONNX, int8), build a container image, register the model with its recipe (commit, data version, metrics).
    🧪 StagingDeploy to a copy of production. Smoke tests: health endpoint, one known picture gives the known answer, latency budget.
    🐤 Canary → 🚀 FullA small share of real traffic first; compare error rate and latency with the old model; then 100%, or automatic rollback.
    👀 MonitorLatency, errors, prediction distribution, input drift, and accuracy once true labels arrive. Alerts can trigger retraining.

    ④ What it looks like in a project (basic structure)

    A pipeline is just a few small scripts (one per step) plus a workflow file that says "run these in this order, stop if one fails". Click a file. These are skeletons that show the idea; they are not meant to be run.

    
  
    
  
    💡 The one rule behind all of it: every step is a script that exits with 0 when OK and non-zero when not.
    The pipeline tool (GitHub Actions, GitLab CI, Jenkins, Azure DevOps…) just runs them in order and stops at the first non-zero exit.

    🤔 Check yourself
    
  
      
    
    1. Why is "the tests passed" not enough to release an ML model?
      
      AnswerTests check the code. The model can still be worse because of the data or the training. You also need data checks and a quality gate on the model's metrics, compared with the current production model.
      2. 
    
    2. What four things must be recorded to rebuild a model exactly?
      
      AnswerThe code version (git commit), the data version, the settings (hyper-parameters and seed) and the environment (library versions / container image).
      3. 
    
    3. What's the difference between continuous delivery and continuous deployment?
      
      AnswerDelivery: every good build is ready to release, but a human presses the button. Deployment: it's released automatically when all gates pass.
      4. 
    
    4. Why keep old models in the registry?
      
      AnswerFor instant rollback, to compare new models against them, and to explain past predictions (audits).
