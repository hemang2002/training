CI/CD for machine learning

A CI/CD pipeline is a robot with a checklist. Every time something changes (the code, the data or the model), the robot runs the same steps in the same order: check it → train it → test it → pack it → give it to a few users → give it to everyone → keep watching. If any step goes wrong, the robot stops, and users simply keep the old model.

👋 New here? The 1-minute version

🧸 Think of a restaurant kitchen

A cook invents a new dish. Before any guest eats it, the chef checks the recipe, checks the ingredients, cooks it and tastes it. Then it goes to one table first. Only if they like it does it go on the menu for everyone. A waiter keeps asking guests how it tastes. The pipeline does exactly this, for ML models.

📖 Hard words, made easy:
CI (Continuous Integration) = check every change automatically CD (Continuous Delivery / Deployment) = release every good change automatically and safely CT (Continuous Training) = retrain automatically when new data arrives or the world changes Pipeline = the fixed list of steps the robot runs Unit test = a tiny automatic check: "give this input, expect this output" Quality gate = the pass mark a model must reach to go further Model registry = a shelf of numbered models (v7, v8…), one labelled "live" Staging = a private copy of the real system, for a final try-out Canary = give the new model to a few users first (like a test table) Rollback = switch back to the old model Drift = the live data slowly stops looking like the training data

① Why do we need it?

😰 Without a pipeline (by hand)

  1. "It works on my laptop." The model was trained with a different library version, and in production it gives other answers.
  2. Nobody ran the tests. A tiny change in preprocessing flips the image colours. Accuracy silently drops.
  3. Which model is live? "model_final_v2_NEW.pth"… trained on which data? Nobody knows.
  4. Rollback takes hours. Someone must find the old file and copy it to the server at night.

😌 With a pipeline (automatic)

  1. Same steps every time, in a clean, identical environment (a container).
  2. Tests and data checks run on every change, in minutes, not "when someone remembers".
  3. Every model has a version and a recipe: this code + this data + these settings.
  4. Rollback is one click: point "production" back to the previous version.

② What is different in ML?

In a normal app, only the code changes, so the pipeline only tests the code. In ML there are three things that can change, and each one can break the app silently: no error message, no crash, just worse answers. So the ML pipeline checks all three.

💻

1. Code

The Python files: how pictures are prepared, the network, the API.

Silent failure: someone changes the picture size from 96 to 64. Everything still runs, but the model gets worse.

Checked by: small automatic tests (🧹 Code checks).

📊

2. Data

The pictures and their labels. New ones arrive every week.

Silent failure: a new camera makes all photos darker, or 10% of the labels are missing.

Checked by: data checks: counts, sizes, missing labels, "does it look like before?" (📊 Data checks).

🧠

3. Model

What training produces from code + data. You can't read it like code.

Silent failure: the total accuracy looks fine, but "cat" is now often wrong.

Checked by: an exam with a pass mark, and a comparison with the live model (🎯 Evaluate).

💡 So: "the tests passed" is not enough in ML. Good code can still produce a bad model, because of bad data.

    👀 MonitorLatency, errors, prediction distribution, input drift, and accuracy once true labels arrive. Alerts can trigger retraining.

    ④ What it looks like in a project (basic structure)

    There is no magic inside. A pipeline is just a to-do list plus a few small scripts:

    📋
    1. The to-do list (ci.yml)
    A workflow file. Each run: line is one step of the checklist, from top to bottom.
    🐍
    2. The workers (validate.py, evaluate.py…)
    Normal Python scripts, one per step. The same code you would write in a notebook.
    🚦
    3. The traffic light
    Each script ends with sys.exit(0) = 🟢 OK, go on, or sys.exit(1) = 🔴 stop the robot.
    ⚙️
    4. The settings (params.yaml)
    All numbers in one file: data version, learning rate, and the pass mark of the exam.

    Click a file on the left. Start with the ⭐ files, in this order. These are short skeletons to show the idea, not meant to be run.

    
  
    
  
    💡 The one rule behind all of it: every step is a script that exits with 0 when OK and non-zero when not.
    The pipeline tool (GitHub Actions, GitLab CI, Jenkins, Azure DevOps…) just runs them in order and stops at the first non-zero exit.

    🤔 Check yourself
    
  
      
    
    1. Why is "the tests passed" not enough to release an ML model?
      
      AnswerTests check the code. The model can still be worse because of the data or the training. You also need data checks and a quality gate on the model's metrics, compared with the current production model.
      2. 
    
    2. What four things must be recorded to rebuild a model exactly?
      
      AnswerThe code version (git commit), the data version, the settings (hyper-parameters and seed) and the environment (library versions / container image).
      3. 
    
    3. What's the difference between continuous delivery and continuous deployment?
      
      AnswerDelivery: every good build is ready to release, but a human presses the button. Deployment: it's released automatically when all gates pass.
      4. 
    
    4. Why keep old models in the registry?
      
      AnswerFor instant rollback, to compare new models against them, and to explain past predictions (audits).
