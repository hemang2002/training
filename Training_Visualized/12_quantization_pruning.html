Making models small

A trained model is just a giant list of numbers (its weights), like 0.0371528… To make it smaller we can ① round every number (keep fewer digits), ② delete the tiny numbers or whole neurons, or ③ train a much smaller student to copy it. The model gets smaller. But does it still work, and is it really faster? Let's find out.

👋 New here? The 30-second version

🧸 Think of it like this

Saving a photo at lower quality makes the file much smaller, and it still looks fine, until you go too far and it looks blocky. Rounding a model's numbers works the same way: a little rounding is invisible, too much breaks it.

👀 Notice this

Going from 32 bits to 8 bits makes the model 4× smaller and it still works just as well. Only when you squeeze very hard does it break.

📱 Why make models small?

📦 Smaller file

Fits on a phone or a small device, and downloads faster.

⚡ Often faster

Small numbers are quicker to move around and to multiply (on hardware that supports them).

🔋 Less energy

Matters a lot on phones, cameras and cheap cloud servers.

① Rounding: allow only a few values

You already know rounding: a price of ₹237 becomes ₹240. The computer does the same with weights, but we choose how many values are allowed, like the marks on a ruler. More marks = more precise, but each number needs more bits to store.

📏 Detailed: the rounding formula

Take all the weights of a layer and find their range, say −0.4 … +0.4. Put 255 evenly spaced marks on that range. For every weight, store only the number of the nearest mark (an integer from −127 to 127, which fits in 1 byte). To use the weight again, multiply the mark number by the spacing.

q = round(x / scale) + zero_point
x̂ = (q − zero_point) × scale

scale = the spacing between marks. zero_point = which integer means 0.0 (it is 0 for symmetric quantization). The small difference x − x̂ is the quantization error. Real int8 schemes pick the range per tensor or per channel, from the weights (and, for activations, from calibration data).

📊 Detailed: one ruler for everyone, or one per channel?

A conv layer has many output channels (kernels), and their weights can have very different sizes. With per-tensor quantization all channels share one ruler, sized for the biggest channel. With per-channel quantization every channel gets its own ruler.

③ Rounding the numbers between the layers: calibration

Rounding the weights is only half of int8. Static int8 (Day 2) also rounds the activations: the numbers that flow from layer to layer while the model runs. Weights are known in advance, but activations depend on the input. So we first run a few calibration examples through the model and write down the range of every layer. At prediction time, every activation is rounded onto a ruler that covers that range; anything outside is clipped to the edge.

✅ What helped

  • ONNX Runtime alone: 8.8 → 1.3 ms, same weights, same size. A fused, pre-planned graph beats Python overhead.
  • Static int8 (with calibration, per-channel): 3.5× smaller and the fastest (0.9 ms), −0.6 pp accuracy. This is what Day 3 serves.

➖ / ❌ What didn't

  • Dynamic int8 in PyTorch: only the last Linear layer is rounded, so a CNN barely changes (9.15 MB, even slower).
  • FP16: half the size, but no speed-up on a CPU. BF16: ≈ 26× slower (227 ms): this CPU has no BF16 hardware, so it's emulated.
  • Unstructured pruning: same file size, same speed (the zeros are still stored and multiplied, challenge 6). 50% without retraining collapses to 33%.

Latencies are medians on one laptop and vary from run to run: compare ratios, and always measure on the machine you will deploy to.

⑤ Pruning methods: which ones really make the model smaller?

Set half of a model's weights to 0 and you'd expect half the file and half the time. Usually you get neither: same file size, same speed. Why? A layer is a table of numbers (8 neurons × 12 inputs below). Pick a method and watch two things: what the computer still has to store, and how many multiplications it still does.

Why only structured pruning pays off everywhere

  • Zeros are still numbers. In float32 a 0 takes 4 bytes, like any other weight. Zipping squeezes long runs of zeros, but that only helps the download. After unzipping, the model is its full size again in memory.
  • × 0 costs as much as × 0.37. The CPU multiplies whole blocks of numbers at once and never checks for zeros, so the time stays the same.
  • A "sparse list" backfires at medium sparsity. For every kept weight it must also store where it is, and that position is often as big as the weight itself. Jumping around memory to find each weight is also slower than reading one neat block.
  • Removing whole neurons / channels makes every table smaller. A smaller, normal table is faster on any hardware. The catch: accuracy drops more at first, so you must retrain.
Detailed: more choices when pruning
  • Global vs per-layer. Global (Day 2: prune.global_unstructured) ranks all weights together, so small layers can be emptied almost completely. Per-layer removes the same % from every layer, which is safer but less clever.
  • Which channel is weakest? Either the sum of its weights (L1 norm), or its BatchNorm "volume knob" γ: a channel with γ ≈ 0 barely contributes (the idea behind "network slimming").
  • Channels are chained. Removing an output channel of one layer also removes an input of the next layer and one BatchNorm entry. Residual connections (x + block(x)) force both sides to stay the same size, which is why the notebook only prunes the inner channels of each block. Libraries such as torch-pruning track these chains automatically.
  • Iterative. Prune a little → retrain → prune a little more. This beats removing everything at once.
  • 2:4 sparsity needs special hardware: sparse tensor cores on NVIDIA A100 / RTX 30-series and newer (up to ≈ 2× faster matrix maths). A normal CPU gains nothing.

⑥ A third way: teach a small student (knowledge distillation)

Rounding and deleting squeeze a given network. Distillation trains a much smaller network, the student, to copy the answers of the big trained teacher. The trick: the teacher can label as many unlabelled examples as we like, and its answers are soft ("80% blue") instead of just "blue", so they carry more information.

🧪 Try this (guess first, then check!)

  1. The rounding game. In ①, start at 1 bit and go up one step at a time. At 1 bit, how many values are allowed? From how many bits are the red mistake lines too small to see?
    AnswerAt 1 bit only 2 values are allowed (−1 and +1), so every weight is pushed to one end and the average mistake is huge (≈ 0.57). Every extra bit doubles the allowed values and roughly halves the mistake: 2 bits ≈ 0.17, 4 bits ≈ 0.04, 8 bits ≈ 0.002. From about 6 bits the red lines are too small to see.
  2. The photo. Drag from 8 bits down. At how many bits do you first see a difference? What does the photo look like at 1 bit?
    Answer8, 7 and 6 bits look identical (no pixel changes by more than 2 out of 255). Around 4–5 bits you start to see stripes in the smooth sky. At 3 and 2 bits it looks like a poster. At 1 bit each colour can only be fully on or off, so the whole photo uses just 6 colours! Smooth, delicate areas show the damage first. In a model it's the same: small, delicate weights suffer first.
  3. How low can the model go? In ②, lower "Bits per weight" one step at a time. When does the After picture stop matching the dots?
    AnswerIt keeps working all the way down to 4 bits (≈ 97%, the same as the original). At 3 bits it starts to break (≈ 88%). At 2 bits it is just guessing (≈ 51%): each layer can only use 3 values (−, 0, +), which is far too few. Tick "per-channel": 3 bits → ≈ 96% and 2 bits → ≈ 80%. Giving every neuron its own ruler helps a lot at low bits.
  4. Smart vs careless deleting. Remove 50% of the weights with "the smallest ones". Then switch to "random ones".
    AnswerDeleting the smallest half: still ≈ 97%. Those weights hardly mattered (look at the wiring: only faint lines disappeared). Deleting a random half: ≈ 54%, almost guessing, because important thick lines were cut too. Simple rule: a small weight has a small influence.
  5. Break it, then heal it. Remove 90% (smallest ones). The model breaks. Now press 🔧 Retrain a little.
    AnswerRight after deleting 90% of the weights the model is broken (≈ 51%, guessing). Retraining for a short while, with the deleted weights kept at 0, brings it back to ≈ 98%, using only 112 of its 1,120 weights! The remaining weights learn to do the job of the deleted ones. Real pruning works like this: delete some, retrain, repeat.
  6. Smaller ≠ faster. After deleting 90%, look at "Model size". Did it shrink?
    AnswerNo! The deleted weights are stored as zeros, and zeros still take space and are still multiplied. To really gain you must store the model in a special "sparse" format, use hardware that skips zeros, or delete whole neurons so the layers really get smaller. Our Live Demo measured exactly this: deleting weights gave no speed-up.
  7. Delete whole neurons. Back to the original. Set "Which ones?" to Whole neurons and remove 50%. Watch accuracy, size and multiplications. Then 75%, then 🔧 Retrain.
    Answer50% of the neurons: 93% accuracy, and the layers really shrink (32 → 16 neurons), so the file drops from 4.63 KB to 1.32 KB and the model needs only 304 multiplications instead of 1,120. 75%: the model breaks (67%, layers 8-8), but after retraining it is back at 98%, with 88 multiplications: 13× less work per answer. That's structured pruning: it can lose more accuracy at first, but unlike deleting single weights it makes the model genuinely smaller and faster on any hardware.
  8. Zeros vs removed rows. In ⑤, set Remove to 50%. Compare ✂️ Smallest weights with 🧱 Whole neurons. Which one saves bytes and multiplications? Which one keeps more strength?
    Answer✂️ keeps 87% of the strength but still stores 384 B and does all 96 multiplications (48 of them are "× 0"). 🧱 stores only 192 B and does 48 multiplications, but keeps only 74%, because some useful weights sit in the removed rows. That's the trade: unstructured = gentle but no gain; structured = real gain, so plan to retrain.
  9. When does a sparse list pay off? Pick 📇 Sparse list and move Remove from 30% upwards. At which % does the file become smaller than the original 384 B?
    Answer30%: 572 B, 50%: 420 B, both bigger than the original, because every kept weight needs a 4-byte position. From 60% (340 B) it's smaller, and at 90% it's only 116 B. For speed the break-even is much later (≈ 95%+ zeros), because finding each weight by its position is slow.
  10. Calibration matters. In ③, try ❌ Only 3 calibration examples, then ❌ Wrong preprocessing. Then keep the wrong preprocessing but go back to 8 bits.
    Answer3 examples: the measured ranges are too narrow, 1.5% of all activations get clipped, and accuracy falls from 97% to 75.5%. With 100 examples: 97%, nothing lost. Wrong preprocessing at 4 bits: the ruler is 6× too long, so the real inputs only use a few of its 16 ticks → 87%. At 8 bits the same mistake is hidden (97.5%): 256 ticks are enough to survive it. A hidden bug is still a bug. On Day 2 (Lab Ex. 3) a forgotten Normalize in calibration dropped the int8 model from ≈ 90% to ≈ 30%.
  11. A student with 70× fewer weights. In ⑥, train the 4-neuron students. Then try the 2-neuron student.
    Answer4 neurons (17 weights): trained on the 20 labels only, 74.5%; trained on the teacher's answers for 1,000 unlabelled dots, 98%, as good as the 1,185-weight teacher (97%). The teacher turns cheap unlabelled data into lessons. 2 neurons: 77.5% vs 82%, both far below the teacher. A student that is too small can't learn the border, however good the teacher.
  12. Read the real numbers. In ④, which technique is fastest? Which one shrinks the file most? Which one is slowest, and why?
    AnswerFastest and nearly smallest: ONNX Runtime static int8 (0.9 ms, 2.61 MB, 89.4%). Smallest: ONNX Runtime dynamic int8 (2.41 MB), but it is 13× slower than static int8 for a CNN. Slowest by far: BF16 on the laptop CPU (227 ms), because the CPU has no BF16 hardware and emulates it. "Smaller" and "faster" are different questions.
  13. Bits vs error (Detailed). Slide from 8 bits down to 2. Watch the SQNR and the blue spikes. About how many dB do you lose per bit?
    AnswerAbout 6 dB per bit (each bit doubles the number of marks and halves the spacing). At 2 bits there are only 3 marks (−s, 0, +s), and most weights collapse to 0.
  14. One bad apple (Detailed). At 8 bits, min–max range, tick "Add ONE outlier". What happens to the scale, SQNR and "rounded to 0"? Then switch Range to "Clip at 99.9th percentile".
    AnswerThe one weight at 0.9 stretches the ruler about 5× wider, so the spacing gets 5× coarser for all 3,999 normal weights. SQNR drops by about 14 dB (42 → 28) and 4× more weights now round to 0. Clipping ignores the extreme value, so the 3,999 normal weights get their fine ruler back. Only the outlier gets a big error, and because that one error is huge, the overall SQNR number looks bad (≈ 13 dB). So clipping is a trade: great for the many normal weights, bad for the rare extreme one. Choosing the range (calibration) is the core decision in static quantization on Day 2.
  15. Per-channel (Detailed). At 8 bits, compare the smallest channel (std 0.01) under both methods. Then try 4 bits.
    AnswerPer-tensor: the small channel only uses a few marks of a ruler built for the big channel, so its SQNR is poor (near 0 dB at 4 bits: the noise is as big as the signal). Per-channel gives every channel roughly the same good SQNR. That's why Day 2's ONNX Runtime export used per_channel=True.

🤔 Check yourself

  1. Why does rounding to 8 bits hurt the model so little?
    AnswerThe rounding mistakes are tiny compared with the weights themselves, like writing 0.03712 as 0.0371. A trained model doesn't notice such small changes.
  2. Your rounded (int8) model is slower than the original on your laptop. How is that possible?
    AnswerSpeed depends on the hardware and software. If your computer has no fast way to multiply 8-bit numbers, or has to keep converting back and forth, it can be slower. We saw this on Day 2 and in the Live Demo: always measure on the machine you will really use.
  3. Which is safer: deleting the smallest weights, or deleting random weights? Why?
    AnswerThe smallest ones. A small weight barely changes the neuron it feeds into, so removing it barely changes the answer. Random deletion also removes big, important weights.
