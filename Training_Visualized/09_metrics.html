Is it any good? Accuracy, precision, recall

"My model is 99% accurate!" sounds great, until you learn that only 1% of the cases were the ones you cared about, and the model simply said "no" every time. One number is never enough. The confusion matrix shows which mistakes a model makes, and precision and recall tell you whether those are the mistakes you can live with.

👋 New here? The 30-second version

🧸 Think of it like this

A smoke alarm that never rings is right 99.9% of the time, because there is almost never a fire. It's also useless. A good alarm must catch the fires (recall) without crying wolf too often (precision).

👆 Do this

  1. In ①, slide How many are sick down to 1% and look at the lazy model's accuracy.

👀 Notice this

Moving the threshold never makes the model smarter. It only trades one kind of mistake (missed cases) for the other (false alarms). You have to decide which one is worse.

📖 Hard words, made easy:
Accuracy = share of all answers that are rightRecall = of all real cases, how many did we catch? Precision = of all our alarms, how many were real?Threshold = how sure the model must be before it says "yes" Confusion matrix = a table of right and wrong answers, split by typeImbalanced data = one class is much rarer than the other

③ The trade-off: what does a mistake cost?

Every threshold gives one (recall, precision) pair. Sliding it from 1 down to 0 draws the precision–recall curve. A better model has a curve closer to the top-right corner. Which point on the curve is "best" depends on what a mistake costs: missing a sick person is usually far worse than one extra check-up.

👀 Moving right = catching more sick people. Moving down = more of the alarms are false. You can't have both for free: to catch the last few sick people you must accept many false alarms.

📏 Detailed: the formulas

accuracy = (TP + TN) / all
recall (sensitivity, TPR) = TP / (TP + FN)
precision = TP / (TP + FP)
F1 = 2 · P · R / (P + R)
specificity = TN / (TN + FP), FPR = 1 − specificity

The ROC curve plots recall against the false-positive rate. Its area (AUC) is the chance that a random sick person gets a higher score than a random healthy one, and it doesn't change with prevalence, which makes it look good on rare-class problems. The precision–recall curve does change with prevalence (challenge 4), so it shows the pain of rare classes honestly. For many classes, "macro" averages treat every class equally, "micro"/"weighted" averages treat every sample equally. Also check calibration: when the model says 80%, is it right about 80% of the time?

🧪 Try this (guess first, then check!)

  1. The lazy model. In ①, set 1% sick. What accuracy does the "always healthy" model get? How many sick people does it find?
    Answer99% accuracy, and it finds 0 of the 10 sick people (recall 0%). At 50% sick the same trick only gets 50%. On imbalanced data, accuracy mostly measures how rare the rare class is.
  2. Read the matrix. Back to 10% sick, quality "OK", threshold 0.50. Read the four boxes and the metrics.
    Answer89 caught, 11 missed, 102 false alarms, 798 correctly calm. Accuracy 88.7%, recall 89%, precision 46.6%. Accuracy looks decent, but 11 of the 100 sick people go home undetected.
  3. Lower the bar. Drag the threshold from 0.50 down to 0.20.
    AnswerRecall rises to 100% (only 0 missed), but false alarms jump to 511, so precision falls to 16.4%. Accuracy even goes down (48.9%). The model didn't change; we only moved the line.
  4. Rare is hard. Keep quality "OK" and threshold 0.50. Compare 10% sick with 1% sick. Watch precision.
    AnswerAt 10% sick: precision 46.6%. At 1% sick: precision 6.5%, with the same model and threshold. With only 10 sick people, even a small share of the 990 healthy people triggering the alarm outnumbers the real cases. This is why screening tests for rare diseases need a second, better test.
  5. Money talks. In ③, set "a missed sick person costs 10 false alarms" and press "Use the cheapest threshold".
    AnswerThe cheapest threshold drops from 0.73 (when both mistakes cost the same) to 0.48. You accept many more false alarms to miss fewer sick people. The "right" threshold is a business decision, not a property of the model.
  6. A better model. Set quality to "excellent", then to "useless".
    AnswerExcellent: the two humps barely overlap, and the curve hugs the top-right corner (best F1 ≈ 0.99). Useless: the humps sit on top of each other, and precision stays near the share of sick people whatever the threshold. Only a better model (better data, features, architecture) moves the whole curve. The threshold only moves you along it.
  7. The weakest class. In ④, click Shirt. What is its recall and precision? Where do its mistakes go?
    AnswerRecall 70.3% (703 of 1,000 shirts found), precision 76.9%. Shirts are mostly mistaken for T-shirt/top (94), Coat (80) and Pullover (70), and the model calls 99 T-shirts "Shirt". The overall accuracy of 91.2% hides a class that is wrong almost one time in three.
  8. The easiest class. Click Bag, then Sneaker.
    AnswerBag: recall 98.9%, precision 97.6%. Bags look like nothing else. Sneaker: recall 96.8%, but 24 sneakers are called Ankle boot and 26 ankle boots are called Sneaker: the footwear classes confuse each other, not the clothes.

🐍 The same thing in Python

from sklearn.metrics import confusion_matrix, classification_report, precision_recall_curve

y_pred = logits.argmax(dim=1)                            # multi-class: the class with the highest score
print(confusion_matrix(y_true, y_pred))                  # rows = true, columns = predicted (as in ④)
print(classification_report(y_true, y_pred, target_names=CLASSES))   # precision / recall / F1 per class

# yes/no problem: choose the threshold yourself
probs = torch.sigmoid(logits).squeeze()
precision, recall, thresholds = precision_recall_curve(y_true, probs)
alarm = probs >= 0.3                                     # not always 0.5!

Always compute metrics on the test set, never on the training set (Lesson 7). For imbalanced training data you can also weight the loss (CrossEntropyLoss(weight=…), BCEWithLogitsLoss(pos_weight=…)) or oversample the rare class, but evaluate with the metrics above either way.

🤔 Check yourself

  1. A fraud detector has 99.5% accuracy on data where 0.5% of transactions are fraud. Impressed?
    AnswerNot yet. "Never fraud" also scores 99.5%. Ask for recall (how much fraud is caught) and precision (how many flagged transactions are really fraud).
  2. For a spam filter, which mistake is worse, and which metric do you watch?
    AnswerA real email in the spam folder (a false positive) is usually worse than one spam in the inbox. Watch precision, and keep the threshold high.
  3. You lower the threshold. Can recall go down?
    AnswerNo. A lower threshold only adds alarms, so it can only catch more (or the same number of) real cases. Precision, however, usually drops.
  4. Your Day-2 int8 model has the same accuracy as FP32 (−0.6 pp). What else would you check before shipping?
    AnswerPer-class recall/precision (did one class, like Shirt, get much worse?), the confusion matrix, and how often the two models agree (Day 2 reports 96% agreement).
