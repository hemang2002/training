Making models small: quantization & pruning

A trained model is just a big list of numbers stored as 32-bit floats (4 bytes each). Quantization stores each number on a coarse ruler with only 256 marks (8 bits), or fewer. Pruning throws the smallest numbers away. Both make the model smaller, and often faster. The question is always: how much accuracy does it cost?

📏 The ruler idea

Take all the weights of a layer. Find their range, say −0.4 … +0.4. Put 255 evenly spaced marks on that range. Now store, for every weight, only the number of the nearest mark (an integer from −127 to 127, which fits in 1 byte). To use the weight again, multiply the mark number by the spacing.

q = round(x / scale) + zero_point
x̂ = (q − zero_point) × scale

scale = the spacing between marks. zero_point = which integer means 0.0 (it is 0 for symmetric quantization). The small difference x − x̂ is the quantization error.

📊 Part B: one ruler for everyone, or one per channel?

A conv layer has many output channels (kernels), and their weights can have very different sizes. With per-tensor quantization all channels share one ruler, sized for the biggest channel. With per-channel quantization every channel gets its own ruler.

🧪 Challenges

  1. Bits vs error (Part A). Slide from 8 bits down to 2. Watch the SQNR and the blue spikes. About how many dB do you lose per bit?
    AnswerAbout 6 dB per bit (each bit doubles the number of marks and halves the spacing). At 2 bits there are only 3 marks (−s, 0, +s), and most weights collapse to 0.
  2. One bad apple (Part A). At 8 bits, min–max range, tick "Add ONE outlier". What happens to the scale, SQNR and "rounded to 0"? Then switch Range to "Clip at 99.9th percentile".
    AnswerThe one weight at 0.9 stretches the ruler about 5× wider, so the spacing gets 5× coarser for all 3,999 normal weights. SQNR drops by about 14 dB (42 → 28) and 4× more weights now round to 0. Clipping ignores the extreme value, so the 3,999 normal weights get their fine ruler back. Only the outlier gets a big error, and because that one error is huge, the overall SQNR number looks bad (≈ 13 dB). So clipping is a trade: great for the many normal weights, bad for the rare extreme one. Choosing the range (calibration) is the core decision in static quantization on Day 2.
  3. Per-channel (Part B). At 8 bits, compare the smallest channel (std 0.01) under both methods. Then try 4 bits.
    AnswerPer-tensor: the small channel only uses a few marks of a ruler built for the big channel, so its SQNR is poor (near 0 dB at 4 bits: the noise is as big as the signal). Per-channel gives every channel roughly the same good SQNR. That's why Day 2's ONNX Runtime export used per_channel=True.
  4. How low can you go? (Part C) Reduce the weight precision step by step. Where does the decision boundary break? Look at the "accuracy vs bits" chart.
    AnswerIt keeps working all the way down to 4 bits (≈ 97%, the same as float32). At 3 bits it starts to break (≈ 88%). At 2 bits it is just guessing (≈ 51%): each layer can only use 3 values (−, 0, +), and the network loses its shape. Now tick "per-channel": 3 bits → ≈ 96% and 2 bits → ≈ 80%. Giving every neuron its own ruler helps a lot at low bits.
  5. Magnitude vs random (Part C). Set sparsity to 50% with "smallest magnitude", then switch to "random".
    AnswerRemoving the smallest half of the weights: still ≈ 97%. Those weights hardly mattered. Removing a random half: ≈ 54%, almost guessing, because random removal also deletes important weights. Simple rule: a small weight has a small influence. The chart shows this for every sparsity: blue stays high much longer than orange.
  6. Prune hard, then heal (Part C). Magnitude pruning at 90%. Note the accuracy. Press 🔧 Fine-tune.
    AnswerRight after removing 90% of the weights the network is broken (≈ 51%, guessing). Fine-tuning means training it again for a while, with the removed weights kept at exactly 0. It comes back to ≈ 98% using only 112 of its 1,120 weights! The remaining weights learn to do the job of the removed ones. Real pruning works like this: remove some, retrain, repeat.
  7. Smaller ≠ faster. After pruning to 90%, look at "Size (dense)". Did it shrink?
    AnswerNo. The zeros are still stored and still multiplied, so a dense matrix full of zeros is exactly as big and as slow. You only gain if you store it in a sparse format or use hardware or kernels that skip zeros (for example 2:4 structured sparsity on recent NVIDIA GPUs), or if you prune whole channels (structured pruning) so the layer really gets smaller. Our Live Demo measured exactly this: unstructured pruning gave no speed-up on CPU.

🤔 Check yourself

  1. Why does int8 usually lose so little accuracy?
    AnswerTrained networks are robust to small noise in their weights. 8-bit rounding error is tiny compared with the weights themselves (SQNR ≈ 40 dB), like writing 0.03712 as 0.0371.
  2. Your int8 model is slower than fp32 on your laptop. How is that possible?
    AnswerSpeed depends on hardware support and the runtime. Without fast int8 kernels (or with lots of quantize/dequantize conversions), int8 can be slower. We saw this on Day 2 and in the Live Demo: always measure on the target machine.
  3. You can afford to lose 0.5% accuracy for a 4× smaller model. Which method do you try first, and what do you check?
    AnswerPost-training int8 quantization (dynamic, or static with calibration). Check accuracy on the validation set, file size and latency on the target hardware. If accuracy drops too much, try per-channel, better calibration, or QAT.
