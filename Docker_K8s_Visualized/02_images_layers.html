Images: a stack of layers

A Dockerfile is a recipe: one instruction per line. docker build runs it and every instruction adds one layer on top of the last. Docker remembers every layer. If nothing changed in a step (and in the steps below it), it reuses the old layer: "CACHED". Get the order right and a rebuild takes seconds instead of minutes.

👋 New here? The 30-second version

🧸 Think of it like this

A lasagne: pasta, sauce, cheese, pasta, sauce… If you want different cheese on top, you don't redo the whole dish, only the top layer. But if you change the bottom layer, everything above it must be made again.

👆 Do this

  1. Press 🏗️ First build: every layer is built.
  2. Press ✏️ I changed app.py: watch which layers say CACHED.
  3. Press 📦 I changed requirements.txt. Then switch on bad order and change app.py again.

👀 Notice this

Rule: a layer is rebuilt if it or anything below it changed. So put what changes rarely (libraries) at the bottom and what changes often (your code) at the top.

② Our real Dockerfile, line by line

# ml-app/api/Dockerfile (simplified: the real file uses a 2-stage build) FROM python:3.12-slim # start from a small Linux + Python COPY api/requirements.txt . # 1) only the list of libraries… RUN pip install -r requirements.txt # 2) …install them (slow, but cached) RUN useradd --uid 1000 appuser # a normal user, not root WORKDIR /app COPY api/app.py api/model_service.py ./ # 3) our code: changes often → near the top COPY models/ ./models/ # the ONNX model files USER 1000 ENV DEFAULT_MODEL=int8 WORKERS=2 # settings you can override at run time EXPOSE 5000 HEALTHCHECK … /health # Docker checks the app is alive CMD exec gunicorn --bind 0.0.0.0:5000 app:app
InstructionWhat it does
FROMThe starting layer: someone else's image (here: slim Debian Linux + Python 3.12).
COPYCopies files from your folder into the image.
RUNRuns a command while building (install things).
ENVA default setting (environment variable).
EXPOSEDocuments the port the app listens on.
CMDThe command that runs when a container starts.

Detail: the real file builds the libraries in a separate "builder" stage and copies only the finished folder (/opt/venv) into the final image, so pip's leftovers never end up in it. That's called a multi-stage build.

🗣️ Explain it like this

  1. "The Dockerfile is a recipe. Every line becomes a layer of the image."
  2. "Docker reuses layers that didn't change: that's the cache. But one changed layer forces every layer above it to be rebuilt."
  3. "So: libraries first, code last. Our rebuild went from 165 seconds to 3 seconds just by ordering the lines well."

🧪 Try this (guess first!)

  1. You changed app.py. Which layers are rebuilt, and how long does it take?
    AnswerOnly COPY app.py and the layers above it (models, settings). pip install says CACHED. Measured: 3.4 s.
  2. You added a library to requirements.txt. Why is it so much slower?
    AnswerThe COPY requirements.txt layer changed, so pip install and everything above it must run again: downloading and installing all libraries. Measured: 164.8 s, of which pip took 78.7 s.
  3. Tick "bad order" and change only app.py. What happens, and why?
    AnswerCOPY . . copies all files (including app.py) below pip install. Any code edit changes that layer, so pip reinstalls every time: ≈ 165 s for a one-line change. That's the classic beginner mistake (problem 3 in Dockerfile.naive).

🤔 Check yourself

  1. Why does our code layer weigh only 24.6 kB when the image is 449 MB?
    AnswerOur code is two small Python files. Almost all the size is the base Linux + Python (≈ 134 MB) and the libraries (189 MB).
  2. What does .dockerignore do?
    AnswerIt lists files Docker should not send to the build (like .git, __pycache__, .venv, *.pth): smaller, faster builds and no secrets copied by accident.
