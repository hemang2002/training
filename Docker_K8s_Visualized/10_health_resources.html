Health checks & resources

Two simple ideas. ① Health checks: Kubernetes regularly asks your app questions ("are you OK?") by visiting a web address, and acts on the answer. ② Resources: every pod gets a budget of CPU and memory, like a hotel booking: a room it reserves, and a maximum it may use.

👋 New here? The 30-second version

🧸 Think of it like this

A nurse visits a patient every few minutes and asks one question. If the patient doesn't answer, the nurse does something: lets them rest, or calls the doctor. In Kubernetes the nurse is the kubelet, the question is a web request like GET /health, and the answer is "200 OK" or nothing.

👀 Notice this

Only two things can happen to a sick pod: it stops getting users (not ready), or it is restarted (not alive / out of memory). That's all.

📖 Words, made easy:
Probe = a regular health questionkubelet = Kubernetes' helper on each machine; it asks the questions /ready, /health = the two web addresses our API answersRequest = resources reserved for the podLimit = the maximum it may useOOMKilled = killed for using too much memory

① The problem: "Running" is not "working"

Kubernetes can see that the container process is running. It can't see what happens inside it. Maybe the models haven't finished loading. Maybe the app is stuck. From outside, all of these look the same:

kubectl get pods
NAME                         READY   STATUS    RESTARTS
cifar-api-68c5fb8c48-ch29k   1/1     Running   0        ← but is it answering users?

So we give Kubernetes a way to ask. Our API has two tiny web addresses made just for this:

  • /health → {"status":"ok"}: "my process is alive and responding"
  • /ready → {"status":"ready","models":["fp32","int8"]}: "my models are loaded, send me work"
🩺 kubelet— GET /ready →📦 API pod
200 OK= yeserror / no answer= no

Real API logs: these knocks arrive every few seconds, signed "kube-probe":

kubectl -n ml-demo logs -l app=cifar-api --tail=3
"GET /ready HTTP/1.1" 200 44 "-" "kube-probe/1.36"
"GET /health HTTP/1.1" 200 16 "-" "kube-probe/1.36"

② Three questions, three reactions

🚀

Startup probe

"Have you finished starting?"

Asks
/ready every 2 s
Patience
up to 30 × = 60 s
If NO in time
🔁 restart the container
Why
Loading models takes time. Don't judge the app before it's ready.
🚦

Readiness probe

"Can you take users right now?"

Asks
/ready every 5 s
Patience
2 NOs in a row
If NO
🚫 no users are sent to it (no restart)
Why
A temporarily busy or half-working pod shouldn't get customers.
❤️

Liveness probe

"Are you still alive?"

Asks
/health every 10 s
Patience
3 NOs in a row
If NO
🔁 restart the container
Why
A stuck app never fixes itself. Turning it off and on again does.

Order: the startup probe goes first. Only after it says "yes" do readiness and liveness start, and then they keep asking forever. All numbers are from our k8s/02-api-deployment.yaml.

    ④ Resources: every pod gets a budget

    In the YAML each pod says how much it needs and how much it may use at most. Think of a hotel: request = the room you book (it's kept free for you), limit = the most you're allowed to use.

    # k8s/02-api-deployment.yaml resources: requests: {cpu: 250m, memory: 256Mi} # booked: ¼ CPU core, 256 MiB limits: {cpu: "1", memory: 512Mi} # never more than 1 core, 512 MiB

    🗣️ Explain it like this

    1. "Running doesn't mean working. So Kubernetes asks three questions by visiting /ready and /health: finished starting? ready for users? still alive?"
    2. "Not ready → no users, no restart. Not alive → restart. That's the whole difference."
    3. "Each pod books CPU and memory (request) and may use up to a maximum (limit). Too much memory → killed. Too much CPU → only slowed down."

    🧪 Try this (guess first!)

    1. In story 3 the app is "not ready" for a while. Is it restarted?
      AnswerNo. Readiness only decides whether users are sent to it. When /ready says yes again, it gets users again. RESTARTS stays 0, exactly like our real /nope test.
    2. In story 4 the app freezes. Which question notices first, and why?
      AnswerReadiness: it asks every 5 s and needs only 2 NOs (≈ 10 s), so users are protected quickly. Liveness asks every 10 s and needs 3 NOs (≈ 30 s) before it restarts, so a short hiccup doesn't cause a restart.
    3. Your model takes 90 s to load. What goes wrong, and what would you change?
      AnswerStory 2: the startup probe gives up after 60 s and restarts the container, which starts loading from zero: a loop. Allow more time: raise failureThreshold (e.g. 60 × 2 s = 120 s).
    4. Set memory to 40 MiB and usage to 150 MiB. Then set CPU to 2.5 cores. Which one kills the pod?
      AnswerOnly memory. Memory can't be "slowed down", so the kernel kills the process (OOMKilled, exit code 137). CPU can be shared out in slices, so the app is just slowed to 1 core.
    5. Add pods until the machine is full. What happens to pod 17?
      AnswerIt stays Pending: its request (250m) doesn't fit anywhere, even if the other pods are idle, because booked rooms stay booked. Fix: smaller requests, or more machines.
