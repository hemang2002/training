Health checks & resources: is it OK, and how much may it use?

"Running" doesn't mean "working". Kubernetes asks every pod three questions, the probes: Have you finished starting? Can you take traffic now? Are you still alive? And every pod says how much CPU and memory it needs (requests) and may never exceed (limits). Our API answers the probes on /ready and /health.

👋 New here? The 30-second version

🧸 Think of it like this

A new employee: first a training period (startup). Each morning: "are you ready to take customers?" (readiness): if not, no customers, but no firing. A security guard checks "is anyone at the desk at all?" (liveness): if the desk stays empty, the person is replaced.

👆 Do this

  1. Press ▶ Start pod and watch the startup probe.
  2. Press 🔌 /ready breaks, then 🧊 app freezes. Compare what happens.
  3. In ②, push memory above the limit.

👀 Notice this

Readiness failing = no traffic, no restart. Liveness failing = restart. Memory above the limit = killed; CPU above the limit = only slowed down.

① The three probes on one API pod

Our real settings (02-api-deployment.yaml): startup every 2 s, up to 30 failures (60 s); readiness every 5 s, 2 failures; liveness every 10 s, 3 failures. The clock runs 4× faster here.

With 40 MiB the API can't even load its models, so it never answers. Depending on timing you'll see these startup-probe failures and restarts, or Last State: Terminated · Reason: OOMKilled · Exit Code: 137 (137 = killed by the kernel). Either way: limits must fit the real app.

🗣️ Explain it like this

  1. "Three questions: finished starting? (startup) ready for traffic? (readiness) still alive? (liveness)."
  2. "Not ready → the Service stops sending traffic, no restart. Not alive → restart. That's why readiness protects users and liveness recovers stuck apps."
  3. "Requests = what the scheduler reserves. Limits = hard caps: too much memory gets the pod killed, too much CPU only slows it."

🧪 Try this (guess first!)

  1. Set model loading to 80 s and start the pod.
    AnswerThe startup probe allows 30 × 2 s = 60 s. After 60 s of failures the kubelet gives up and restarts the container, which starts loading again… forever. If your model is big, raise failureThreshold.
  2. Break /ready, wait, then fix it. Was the pod restarted?
    AnswerNo. After 2 failed checks it leaves the Service (no traffic); after the next success it comes back. RESTARTS stays 0. Exactly what we saw with /nope.
  3. Freeze the app. How long until the restart?
    AnswerLiveness checks every 10 s and needs 3 failures in a row: about 20–30 s. Readiness notices first (after ~10 s) and stops the traffic.
  4. Set the memory limit to 40 and usage to 150.
    AnswerOOMKilled, exit code 137, restart, killed again: CrashLoopBackOff. Our docker stats showed the API using 53.5 MiB while idle, and it needs more while loading models and serving (the Day-4 README measured ≈ 150 MiB). 40 MiB is below even the idle need.
