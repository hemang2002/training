Running a container: ports, settings, lifecycle

docker run turns an image into a running container. A container is sealed by default: nothing from outside can reach it. You open a door with -p host:container, change settings with -e NAME=value, and look inside with logs and exec. The same image, many different runs.

👋 New here? The 30-second version

🧸 Think of it like this

A container is a flat in a big building. The app lives in flat 5000. -p 8000:5000 means: "a visitor who rings the building's door 8000 is sent up to flat 5000". Without -p, nobody can visit.

👆 Do this

  1. In ①, press Send request. Then change the ports and try again.
  2. Set the app to listen on 127.0.0.1. What happens?
  3. In ③, click through the lifecycle buttons.

👀 Notice this

You visit localhost:HOST; the app always listens on its CONTAINER port. And inside a container the app must listen on 0.0.0.0, or the door leads nowhere.

① Opening a door: -p host:container

docker run -d --name api -p 8000:5000 cifar-api:v1

② Same image, different settings: -e

The image has defaults baked in (ENV DEFAULT_MODEL=int8). -e overrides them when the container starts. No rebuild: that's why settings go in environment variables, not in the code.

🗣️ Explain it like this

  
  1. "docker run starts a container from an image. -p 8000:5000 opens a door: PC port 8000 goes to container port 5000."
    2. 
    
  2. "Inside the container the app must listen on 0.0.0.0. 127.0.0.1 would mean 'only me', so the door leads nowhere."
    3. 
    
  3. "-e changes settings without rebuilding. logs, exec and stats let us look inside."






  
🧪 Try this (guess first!)

  
    
    
  1. Run with -p 8000:5000, then open http://localhost:5000/health. Works?
      
    AnswerNo: nothing on your PC listens on 5000. The door is 8000. Rule: host port (left) is what you type in the browser; container port (right) is where the app listens.
    2. 
    
  2. Set the container port to 80 (-p 8000:80).
      
    AnswerFails: the door leads to flat 80, but the app lives in flat 5000. The right-hand number must match the port the app listens on (EXPOSE 5000 in the Dockerfile).
    3. 
    
  3. Set the app to 127.0.0.1. Is the app broken?
      
    AnswerNo! It runs fine inside the container. We tested it for real: from outside, curl http://localhost:5003/health got an empty reply, but
      docker exec demo-bad python -c "…urlopen('http://127.0.0.1:5000/health')…" answered b'{"status":"ok"}'. 127.0.0.1 inside a container means "only this container".
    4. 
    
  4. What's the difference between docker stop and docker rm?
      
    Answerstop ends the process (status Exited); the container still exists and can be started again. rm deletes it. docker rm -f does both at once.
