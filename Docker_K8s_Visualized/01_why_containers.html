Why containers? "It works on my machine!"

Our Day-3 API works on your laptop. You copy it to a server and it crashes: a different Python, a different numpy, the model files are missing. A container fixes this by shipping the app together with everything it needs: the right Python, the libraries, the model files and the start command. In one box.

👋 New here? The 30-second version

🧸 Think of it like this

Moving house: you don't send "a list of furniture" and hope the new house has the same furniture. You pack everything into a shipping container. Every ship, truck and crane in the world can carry that same standard box without opening it.

② A container is not a virtual machine

A virtual machine (VM) pretends to be a whole computer: it carries a complete operating system, gigabytes big, and takes minutes to boot. A container is just an isolated process on your computer. It shares your operating system's core (the kernel) and only carries the app and its libraries.

On Windows and macOS, Docker Desktop runs one small Linux VM in the background (WSL 2 on Windows), and all containers share it.

③ Four words to remember

📝 Dockerfilethe recipe→ docker build → 📦 Imagepacked box, read-only→ docker run → 🟢 Containerthe running copy
📦 Image⇄ docker push / pull ⇄🏪 RegistryDocker Hub: a shop for images

One image can start many containers, like one cake mould makes many cakes. Our API image is called cifar-api:v1: name cifar-api, tag v1.

🗣️ Explain it like this

  1. "Code alone is not enough: it needs the right Python, libraries and files. Servers never match your laptop exactly."
  2. "An image packs the app with everything it needs. A container is that image running."
  3. "The server now needs only Docker. The same box runs the same way on a laptop, a server or the cloud."

🧪 Try this (guess first!)

  1. With "only the code", set the server to exactly match your laptop (3.12, 2.5, 1.30, copied). Does it work? Is that realistic?
    AnswerYes, it works, but only because you made the server identical by hand. With 10 servers, 5 developers and updates every week, keeping them identical is almost impossible. The container makes it automatic.
  2. With "a container image", set every server option to the worst value. What happens?
    AnswerIt still works. The container brings its own Python 3.12, numpy, onnxruntime and model files. The server's own versions don't matter at all.
  3. How many containers can you start from one image?
    AnswerAs many as you like: the image is read-only, and each container gets its own thin writable layer. That's how Kubernetes will run 2, 4 or 6 copies of our API (page 7).

🤔 Check yourself

  1. Image or container: which one is running and uses CPU?
    AnswerThe container. The image is only the packed, frozen template stored on disk.
  2. Why does a container start in seconds but a VM in minutes?
    AnswerA container doesn't boot an operating system; it starts one process (our gunicorn server) on the already-running kernel.
