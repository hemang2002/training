Deployment: "always keep N copies, and update them safely"

A Deployment is the manager of our pods. We tell it: "run 2 copies of cifar-api:v1". It creates a ReplicaSet, which creates the Pods. A pod dies? It makes a new one. We want 4? It adds 2. New version? It swaps pods one by one, so users never see downtime, and it can roll back in one command.

👋 New here? The 30-second version

🧸 Think of it like this

A shop manager must always have 2 cashiers at the tills. One goes home sick: the manager calls in someone new. New uniforms: they swap cashiers one at a time, so a till is never empty.

👆 Do this

  1. Click a pod to kill it. Watch it come back.
  2. Change replicas.
  3. Press 🚀 Update to v2, then 💣 Update to a broken version, then ↩ Roll back.

👀 Notice this

During an update there are never fewer than 2 ready pods (maxUnavailable: 0). A broken version stalls instead of taking the app down.

📖 Words, made easy:
Deployment = the manager (what you write)ReplicaSet = one team of identical pods for one version replicas = how many copiesRolling update = replace pods a few at a timeRollback = go back to the previous version

② The YAML: k8s/02-api-deployment.yaml

apiVersion: apps/v1 kind: Deployment metadata: {name: cifar-api, namespace: ml-demo} spec: replicas: 2 # how many copies strategy: rollingUpdate: maxSurge: 1 # at most 1 extra pod during an update maxUnavailable: 0 # never fewer ready pods than replicas selector: matchLabels: {app: cifar-api} # "my pods are the ones labelled app=cifar-api" template: # the pod to copy (page 6) metadata: labels: {app: cifar-api} # MUST match the selector spec: containers: - name: api image: cifar-api:v1 # change this → rolling update

The template is simply the pod from page 6. The Deployment stamps out replicas copies of it and gives each a random name: cifar-api-68c5fb8c48-ch29k = Deployment name + ReplicaSet id (one per version of the template) + random pod id.

Labels and selectors are how Kubernetes objects find each other: the Deployment manages every pod that carries the label app=cifar-api. The Service (next page) finds them the same way.

🗣️ Explain it like this

  1. "A Deployment is a manager: 'keep 2 copies of this pod running'. It uses a ReplicaSet to do the counting."
  2. "Kill a pod and a new one appears within seconds. Change replicas and it adds or removes pods."
  3. "A new version starts new pods first and removes old ones only when the new ones are ready. Broken version? It stalls, users still get the old one, and rollout undo brings us back."

🧪 Try this (guess first!)

  1. With replicas 2, maxSurge 1, maxUnavailable 0: during an update, what's the largest number of pods at once? The smallest number of ready pods?
    AnswerAt most 3 pods (2 + 1 surge); never fewer than 2 ready (2 − 0). That's zero downtime, at the price of one extra pod's CPU and memory for a moment.
  2. Set maxUnavailable to 1 and deploy the broken version.
    AnswerNow Kubernetes may remove one old pod before the new one is ready, so you are left with 1 ready pod and 1-2 broken ones: half the capacity is gone. With maxUnavailable: 0 (our file) the old pods all stay.
  3. Why are there three ReplicaSets after our real test?
    AnswerOne per version of the pod template: the first version, the settings change (rollout restart), and the broken image. Old ones are scaled to 0 but kept (revisionHistoryLimit: 3) so rollout undo can switch back instantly.
