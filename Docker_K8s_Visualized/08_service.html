Service: one fixed address for a changing group of pods

Pods come and go, and every new pod gets a new IP. So how does the UI find the API? A Service gives the group a fixed name and address (cifar-api:5000) and spreads the requests over all pods that carry the right label and are ready.

👋 New here? The 30-second version

🧸 Think of it like this

A call-centre number. You always dial the same number; behind it, whichever agent is free and working today picks up. Agents change shifts all the time, and the number never changes.

👀 Notice this

The Service doesn't care about pod names or IPs. It picks pods by label (app=cifar-api), and only the ready ones.

📖 Words, made easy:
Service = fixed name + address in front of podsSelector = "the pods with this label"Endpoints = the pod addresses behind it right now ClusterIP = reachable inside the clusterNodePort = also reachable from your PC on a port like 30080

② Three kinds of Service

  

    
🔒 ClusterIP our API
Only reachable inside the cluster, by name. The UI uses http://cifar-api:5000. Your browser can't reach it: good, the API stays private.

    
🚪 NodePort our UI
Also opens a port (30000–32767) on every node. Our UI: nodePort: 30080 → open http://localhost:30080 on your PC.

    
🌍 LoadBalancer
In a cloud, asks the provider for a public IP address in front of the Service. The usual way to go public (costs money on most clouds).

  

  
For many web apps on one address (shop.com/, shop.com/api) there's also an Ingress: one entry point that routes by host name or path. Example: k8s/extras/ingress.yaml.

A typo in the selector

      
kubectl -n ml-demo patch service cifar-api -p "{\"spec\":{\"selector\":{\"app\":\"cifar-apii\"}}}"
service/cifar-api patched
kubectl -n ml-demo get endpoints cifar-api
NAME        ENDPOINTS
cifar-api   <none>       ← no pod has the label "cifar-apii"
kubectl -n ml-demo exec deploy/cifar-ui -- python -c "…urlopen('http://cifar-api:5000/health')…"
urllib.error.URLError: <urlopen error [Errno 111] Connection refused>

      
No error anywhere else: the pods are healthy, the Service exists. Silent label mistakes are why kubectl get endpoints is the first thing to check.
